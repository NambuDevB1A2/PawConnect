# 고객 요구사항

최신: 2026-07-10


## 고객 요구사항 - PawConnect DB

- 서비스는 회원(User)/보호소(Shelter)/보호동물(Animal)/입양신청(Adoption)/반려동물 자랑 게시글(PetPost) 관리가 기본적으로 필요하다.

#### 회원 시스템(User)

- 회원은 고유번호(UUID, PK)가 자동으로 발급되어야 한다.
- 회원의 이메일, 비밀번호, 닉네임은 누락되면 안되며, 비밀번호는 해시 처리하여 저장한다.
- 회원의 역할(Role)은 비회원(GUEST)/일반 사용자(USER)/보호소 관리자(SHELTER)/홈페이지 관리자(ADMIN) 중 하나로 관리되며 누락될 수 없다.
- 회원 상태(status)는 정상 이용(ACTIVE)/이용 정지(SUSPENDED)/휴먼(INACTIVE)/탈퇴(WITHDRAWN) 중 하나로 관리하며, 기본 값은 ACTIVE이다. (회원 탈퇴시 회원 정보를 물리적으로 삭제하지 않고 상태값만 변경한다.)
- 회원은 보호소(shelterId)에 소속될 수 있으며, 이는 선택 사항이다. (보호소 관리자 회원만 특정 보호소에 연결되고, 일반 사용자, 홈페이지 관리자는 비워둘 수 있다.)
- 회원의 프로필 사진은 선택 사항이며, 미입력시 기본 이미지가 사용된다.
- 회원의 생성일(createdAt)은 자동으로 기록되며, 수정일(updatedAt)은 정보 변경시 갱신된다.

#### 보호소(Shelter, ShelterImage)

- 보호소는 이름, 주소, 전화번호(-없이 숫자로 이루어진 텍스트), 운영시간, 소개말이 누락되면 안된다.
- 보호소 이름은 최대 100자, 소개말은 최대 500자까지 등록된다.
- 보호소 배너 사진은 선택 사항이며, 미입력시 기본 이미지가 사용된다.
- 보호소 사진은 보호소마다 여러 장을 등록할 수 있도록 별도 테이블(ShelterImage)로 분할 관리한다.
- 보호소의 생성일/수정일도 자동으로 기록, 갱신되어야 한다.

#### 보호동물(Animal, AnimalDetail, AnimalImage)

- 보호동물은 보호소에 반드시 귀속되어야 하며, 존재하지 않는 보호소로는 등록할 수 없다.
- 보호동물의 동물 종류(species)와 품종(breed)는 자유 입력이 아닌, 별도 마스터 테이블(AnimalSpecies, AnimalBreed)에서 선택하는 구조로 관리한다. (품종은 반드시 하나의 동물 종류에 속한다. Animal에 저장되는 species 값은 반드시 breed가 속한 species와 일치해야 한다.)
- 보호동물의 기본 정보 (이름, 종류, 품종, 성별, 중성화 여부, 나이, 추정 나이 여부, 입양 상태, 몸무게, 썸네일 이미지)와 부가 정보(공고 시작일/마감일, 발견 장소, 특이사항, 소개말, 건강 상태)는 각각 Animal, AnimalDetail 테이블로 분리하여 1:1로 관리한다. (자주 조회되는 목록용 필드와 상세 조회 전용 필드를 나눈 성능 최적화용 분할이다.) 생성일은 Animal에서만 관리하고, 수정일은 Animal과 AnimalDetail 양쪽에서 각자 갱신 시점을 독립적으로 관리한다.
- 성별(gender)은 MALE/FEMALE/UNKNOWN 중 하나로 관리하며, 중성화 여부(isNeutered)는 별도의 boolean 필드로 관리한다.
- 나이(age)는 숫자로 관리하되, 개월 수로 측정한다. 보호소가 정확한 나이를 모르는 경우를 위해 추정 나이 여부(isEstimatedAge) 플래그를 함께 관리한다.
- 몸무게는 소수점 둘째 자리까지 표시되어야 한다. (Numberic(5, 2))
- 발견 장소는 최대 50자, 특이사항은 최대 100자, 소개말과 건강상태는 최대 500자까지 등록된다.
- 보호동물 사진은 한 게시글당 여러 장을 등록할 수 있도록 별도 테이블(AnimalImage)로 분할 관리하며, 최소 1장 이상 등록되어야 한다.
- 목록 노출용 썸네일 이미지는 필수 입력값이다.

#### 입양 신청(Adoption, AdoptionDetail )

- 입양 신청은 실존하는 회원과 실존하는 보호동물에 대해서만 등록할 수 있다.
- 입양 신청의 상태 정보(status)는 신청서 상세 내용(신청자 이름, 신청자 이메일, 전화번호, 주소, 상세 주소, 반려동물 양육 경험, 상세, 기간, 거주 형태, 반려동물 사육 가능 여부, 가족 구성, 어린 아이 여부, 가족 동의 여부, 입양 목적, 예방 접종 가능, 병원 치료 가능, 산책 및 운동 가능, 평생 책임 양육 동의, 추가 전달사항)은 각각 Adoption, AdoptionDetail 테이블로 분리하여 1:1로 관리한다. (자주 조회되는 목록용 필드와 조회 전용 필드를 나눈 성능 최적화용 분할이다.) 생성일은 Adoption에서만 관리하고, 수정일은 Adoption과 AdoptionDetail 양쪽에서 각자 갱신 시점을 독립적으로 관리한다.
- 반려동물 양육 경험 여부는 처음 키움(NONE)/과거 경험(PAST)현재 양육 중(CURRENT) 중 하나로 관리하며, 양육 경험이 있다면 양육 경험 상세(최대 100자)와 반려동물 양육 경험 기간(1년 미만/1~3년/3~5년/5년 이상)을 추가로 입력 받는다.
- 거주 형태는 아파트/빌라/단독주택/오피스텔/기숙사 중 하나로, 사육 가능 여부는 가능/불가능/확인 필요 중 하나로 관리한다.
- 가족 구성은 1명/2명/3명/4명 이상 중 하나로, 어린 아이 여부는 없음/7세 미만/7세 이상 중 하나로, 가족 동의 여부는 예/아니오(Boolean) 값으로 관리한다.
- 입양 목적(최대 100자)는 필수 입력 항목이다.
- 반려동물 양육 가능 여부 서약은 예방접종 가능 여부, 병원 치료 가능 여부, 산책 및 운동 제공 가능 여부, 평생 책임 양육 동의 여부의 4개 항목을 각각 별도의 예/아니오(Boolean) 값으로 관리한다.
- 추가 전달사항(최대 500자)는 필수 입력 항목이다.
- 입양 신청 상태(status)는 대기/상담/면접/추가면접/임시보호/최종심사/승인/거절/신청취소 중 하나로 관리하며, 상태 변경은 보호소 관리자 측에서만 가능하다. (신청 취소의 경우에만 일반 사용자도 상태 변경이 가능하다.)

#### 약관(Agreement, UserAgreement, AdoptionAgreement)

- 약관(이용약관, 개인정보 처리방침 등)은 별도의 약관 마스터 테이블(Agreement)에서 제목, 내용(선택)을 관리한다.
- 회원가입시 약관 동의 여부는 회원별 약관 동의 테이블(UserAgreement)에, 입양 신청시 약관 동의 여부는 입양 신청별 약관 동의 테이블(AdoptionAgreement)에 각각 기록하며, 동의 여부(isAgreed)와 동의 시각(agreedAt)을 함께 등록한다.

#### 반려동물 자랑 게시글(PetPost, PetPostImage)

- 회원은 자신이 기르는 반려동물을 자랑하는 게시글(PetPost)을 작성할 수 있으며, 제목(최대 50자)과 내용(최대 500자)를 필수로 등록해야한다.
- 반려동물 자랑 게시글 사진은 한 게시글당 여러 장을 등록할 수 있도록 별도 테이블(PetPostImage)로 분할 관리한다.
- 반려동물 자랑 게시글의 생성일/수정일도 자동으로 기록, 갱신되어야 한다.

## 관계성 핵심

- **User : Shelter (N:1 관계, 선택적)**
    - 보호소 관리자(User)는 하나의 보호소(Shelter)에 소속될 수 있으며, 하나의 보호소는 여러 보호소 괸리자를 가질 수 있다. 일반 사용자, 홈페이지 관리자는 보호소를 비워둘 수 있다.
    
- **Shelter : ShelterImage (1:N 관계)**
    - 하나의 보호소는 여러 장의 보호소 사진을 가질 수 있다.
    
- **Shelter : Animal (1:N 관계)**
    - 하나의 보호소는 여러 건의 보호동물을 등록할 수 있으며, 하나의 보호동물은 반드시 하나의 보호소에만 귀속된다.
    
- **Animal : AnimalDetal (1:1 관계)**
    - 하나의 보호동물은 정확히 하나의 상세 정보 레코드를 가진다.
    
- **Animal : AnimalImage (1:N 관계)**
    - 하나의 보호동물은 여러 장의 보호동물 사진을 가질 수 있다.
    
- **AnimalSpecies : AnimalBreed (1:N 관계)**
    - 하나의 동물 종류(예: 개, 고양이)는 여러 품종을 가질 수 있으며, 하나의 품종은 반드시 하나의 동물 종류에만 속한다.
    
- **AnimalSpecies : Animal (1:N 관계), AnimalBreed : Animal (1:N 관계)**
    - 하나의 동물 종류/품종은 여러 보호동물에 참조될 수 있다.
    
- **User : Adoption (1:N 관계), Animal : Adoption (1:N 관계) ⇒ User : Animal (N:M 관계)**
    - 한 명의 회원읜 여러 번의 입양을 신청할 수 있고, 하나의 보호동물도 여러 건의 입양 신청을 받을 수 있다. 하나의 입양 신청 건은 반드시 한 명의 회원과 하나의 보호동물에만 귀속된다.
    
- **Adoption : AdoptionDetail (1:1 관계)**
    - 하나의 입양 신청 건은 정확히 하나의 신청서 상세 정보 레코드를 가진다.
    
- **Agreement : UserAgreement (1:N 관계), User : UserAgreement (1:N 관계) ⇒ Agreement : User (N:M 관계)**
    - 하나의 약관은 여러 회원의 동의 기록을 가질 수 있고, 한 명의 회원도 여러 약관에 각각 동의할 수 있다.
    
- **Agreement : AdoptionAgreement (1:N 관계), Adoption : AdoptionAgreement (1:N 관계) ⇒ Agreement : Adoption (N:M 관계)**
    - 하나의 약관은 여러 입양 신청 건의 동의 기록을 가질 수 있고, 하나의 입양 신청 건도 여러 약관에 각각 동의할 수 있다.
    
- **User : PetPost (1:N 관계)**
    - 한 명의 회원은 여러 건의 반려동물 자랑 게시글을 작성할 수 있고, 하나의 게시글에는 반드시 한 명의 작성자에게만 귀속된다.
    
- **PetPost : PetPostImage (1:N 관계)**
    - 하나의 반려동물 자랑 게시글은 여러 장의 사진을 가질 수 있다.

## 구현 시 참고 사항

- **Animal.species 정합성 강제 방식**
    
    species는 breed로부터 도출 가능한(이행적 종속)이므로, 실제 구현 단계에서는 species와 breed.species가 항상 일치하도록 강제해야한다.
    
- **부모/상세 테이블의 수정일(updatedAt) 분할 관리**
    
    AnimalDetail/AdoptionDetail이 각자 updatedAt을 갖게 되면서, 목록용 필드(부모)와 상세 정보 필드(자식)의 마지막 수정 시점을 독립적으로 추적할 수 있다. “게시글이 언제 마지막으로 수정되었는지” 하나의 값을 보여줘야 하는 화면이 있다면, 두 updatedAt 중 최근 값을 선택하는 로직이 API/서비스 레벨에서 필요한다.
    

## 서비스 확장성 시, 고려사항

- **하나의 보호소에 여러 명의 보호소 관리자 정책**
    
    현재 DB는 하나의 보호소에 여러 명의 보호소 관리자를 둘 수 있다. MVP에서는 기획되지 않은 사항이지만 업데이트가 된다면 참고.
    
- **성향테스트(PersonalityTest) 엔티티 미설계**
    
    요구사항 목록(U-401~U-404)에는 있으나 성향테스트 결과는 DB에 저장되지 않는다. 추후 결과 데이터 저장 예정이 있다면 참고.
    
- **입양 상태 변경 이력(로그) 테이블**
    
    상태 변경 과정을 추적하기 위한 이력 테이블이 아직 구현되지 않았다. 추후 추가 예정이 있다면 참고.
    
- **보호소/보호동물 삭제(소프트 삭제) 정책**
    
    회원(User)은 상태값(status)으로 소프트 삭제가 가능하지만, 보호소(Shelter)와 보호동물(Animal)에는 아직 유사한 상태 관리 필드가 없다. 추후 소프트 삭제 정책을 실시한다면 참고.
